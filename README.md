# fit-log

A workout logger for Android, built for one person and a few friends. No server,
no accounts, no sync. The log is a single JSON file on the phone.

## Why it works the way it does

This replaces a plaintext file kept since August 2025, which looked like this:

```
3/4/26 A
Squat 200
Bench 150
Row 130 (-1/-2)
B curl 20 (-3)
Leg raise 12/12/6
```

That notation is dense because **it only records deviations from the plan**.
`Squat 200` means five sets of five at 200, all completed. `Row 130 (-1/-2)`
means two of those five sets fell short, by one rep and by two. `B curl 20`
is twenty pounds of plates on the EZ bar, not a twenty pound bar.

(The example above is illustrative; the real log is not in this repository.)

So the app logs by exception too: it pre-fills the whole session from your
routine and what you actually lifted last time, and a clean workout is one tap.
A logger that asked for sixty taps per session would be worse than the text
file it replaces.

## Repository layout

```
text_log                      the original log. Ground truth. NOT IN THIS REPO.
importer/
  program_config.py           targets, eras, equipment changes, ambiguity rules
  fitlog_import.py            parser, emitter, and four validation layers
  test_parse.py               28 tests, driven by real lines from text_log
out/                          generated by the importer. NOT IN THIS REPO.
  fitlog.json                 the artifact the app reads
  import_report.md            assumptions, review queue, diff classification
app/                          the Android app (Kotlin + Jetpack Compose)
```

`text_log` and `out/` are gitignored. This repository is public and they are
personal training data, so they live only on the machine that generates them,
backed up separately. Everything here is the code that processes them; clone it
and point the importer at your own log.

## Building the app

JDK 21 and the Android SDK. Gradle handles the rest.

```sh
./gradlew testDebugUnitTest     # 89 JVM tests: the parser's counterpart in Kotlin
./gradlew installDebug          # build and push to a connected phone
```

Debug builds seed themselves from `app/src/debug/assets/fitlog.json` on first
run, so there is something to look at. That directory is gitignored and debug
only — a release build starts empty, and no personal data has ever been in an
APK you could hand to someone.

### Releases

```sh
./gradlew assembleRelease       # app/build/outputs/apk/release/app-release.apk
```

Two things to know before you hand that file to anyone.

**Bump `versionCode` in `app/build.gradle.kts` every single time.** Android
refuses to install an APK whose version code is not higher than the one already
on the phone. The only way out of that is uninstalling, and uninstalling deletes
that phone's `fitlog.json`.

**The signing key is the part that cannot be replaced.** Android identifies an
app by its key, not its name. Build the release with a different key and no
existing install will accept the update — every friend has to uninstall, losing
their log. The source here can always be rebuilt; the key cannot be regenerated.

Signing is configured from `keystore.properties` at the repo root, which points
at a keystore outside the repo entirely. Both are gitignored, and this repo is
public. A fresh clone has neither, so `assembleRelease` there produces an
unsigned APK rather than a build error.

```
keystore.properties           storeFile / storePassword / keyAlias / keyPassword
~/keys/fit-log-release.jks    4096-bit RSA, 100 year validity
```

Keep a copy of both, together, somewhere that is not this machine.

### Installing it for a friend

Send them the APK. They will need to allow installs from whatever app they
opened it with. On first run the app is empty: **Routines** to build their days,
and that is the whole setup — nothing is shared between installs, so their log
never touches yours.

Tell them about **Settings → Export as JSON** before they log anything real.
Uninstalling the app deletes its storage, and that export is the only backup.

## Running the importer

Python 3.11+, standard library only. Nothing to install.

```sh
cd importer
python3 fitlog_import.py /path/to/your/text_log --out ../out
python3 test_parse.py
```

Most tests run against inline examples and work on a fresh clone. The one test
that walks a whole log skips itself when no `text_log` is present.

Useful flags:

| Flag | What it does |
|---|---|
| `--explain 257` | dump one source line's full parse tree |
| `--tracks` | print every light/heavy track assignment with its margin |
| `--no-roundtrip` | skip validation (faster while iterating) |

**`program_config.py` is the file you edit.** The log never recorded target
reps — they appear exactly once in 1047 lines — so the program is an input, not
something the importer can infer. Every guess in that file is marked
`ASSUMPTION`. Change one and re-run; the importer is deterministic.

## Validation

The importer exits non-zero unless all four layers pass, so a bad import cannot
reach the phone by forgetting to read the report.

| Layer | What it proves |
|---|---|
| L1 line bijection | every one of the 1047 lines is accounted for exactly once |
| L2 semantic round trip | all 152 sessions survive being written back out and re-parsed |
| L3 literal diff | every surface difference is provably semantically empty |
| L4 invariants | counts, the 2.5 lb weight grid, AMRAP targets, catalog references |

L3 does not pattern-match strings. It parses both the original and the
regenerated line and compares the result, so a real change cannot hide behind a
string rule.

## Two things the data model gets right

**Weight means five different things**, and each set stores which one it is:

| Kind | The number is |
|---|---|
| `barbell_total` | bar plus plates |
| `bar_added` | plates added to the EZ curl bar, bar excluded |
| `dumbbell_each` | one dumbbell |
| `bodyweight` | no external load |
| `time` | seconds |

Without this, `B curl 17.5` and `Skull 15` quietly destroy every record
calculation. Nothing is re-inferred when the data is read.

**Some lifts run two progressions at once.** Squat and deadlift alternate light
and heavy days on separate tracks, so records and graphs group by
`(exercise, load kind, track)`. Compared track-unaware, a light deadlift looks
like a regression from the heavy day before it, and the chart becomes a
meaningless sawtooth.

The text log never recorded which track a session was, so historical tracks are
*reconstructed*. Every one carries `trackOrigin` and `trackConfidence` saying
so, and anything near a boundary is flagged for review rather than guessed.
